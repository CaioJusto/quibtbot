## Corrigido

### Execução de runs (`packages/adapters`, `apps/worker`)

| Onde | O que acontecia | Como ficou |
| --- | --- | --- |
| `run-lease.ts` (novo), `executor.ts` | `leaseExpiresAt`/`leaseFence` eram escritos e nunca lidos: um segundo `run.continue` executava o mesmo run de novo. | Aquisição por compare-and-swap num único `updateMany`; renovação por um timer (2 s) que também detecta cancelamento; conclusão cercada por fence. |
| `run-lease.ts`, `apps/worker/src/handlers.ts` (novo) | Worker morto deixava o run `running` até o lock de 4 h do Graphile. | Reaper `run.reap` (self-rescheduling, `jobKey` único) devolve o run à fila ou falha de forma controlada após 3 tentativas. Linhas anteriores ao lease (`leaseExpiresAt` nulo) só são resgatadas após 4 h, para não requeuar um run que um worker antigo ainda esteja executando durante um deploy. |
| `executor.ts` | Duas mensagens rápidas rodavam **dois agentes no mesmo bot**, no mesmo computador. | `botBusyWith` serializa por bot (lease vivo bloqueia; lease morto e pausas não bloqueiam; o próprio run nunca se auto-bloqueia). Ao terminar um turno, o `queued` mais antigo do bot é acordado (FIFO), com reenfileiramento de segurança em 5 s. |
| `executor.ts` (`ask_bot`), `peer-wait.ts` (novo) | Busy-wait de até 4 min ocupava um slot do worker; quatro bots perguntando esgotavam os 4 slots e todos expiravam. | Checkpoint + pausa (mesmo fluxo da aprovação): o slot volta na hora e o run é acordado quando o par termina. |
| `pi-runtime.ts`, `approval-wait.ts` | A pausa de `ask_bot` devolvia ao modelo "Waiting for the user's approval." — o run esperava outro **bot**, não o usuário, e isso entrava no histórico. | Cada pausa carrega o próprio texto. |
| `executor.ts` (streaming) | `thread.progress` a cada 80 ms e um `run.findUnique` **por token** só para checar cancelamento. | Cadência de 400 ms sem republicar texto igual; cancelamento vem do watcher do lease. ~12 consultas/s → ~0,5/s. Formato do evento inalterado (contrato dos clientes preservado). |
| `executor.ts` (`wakeRoutine`) | Task/run e reagendamento fora de transação: falha no meio + retry duplicava o run. | Uma transação; o próximo tick só é enfileirado após o commit. |
| `wakeup.ts` | `InMemoryWakeupDriver` vazava um timer por job (nunca removia após disparar) — grave com tarefas que se reagendam. | Timer removido ao disparar. |
| `e2b-sandbox.ts` | Falha após `Sandbox.create` deixava sandbox paga rodando sem referência. | `preparedOrKilled()`. |

### API, dados e cobrança (`apps/api`, `packages/core`, `memory`, `auth`)

| Onde | O que acontecia | Como ficou |
| --- | --- | --- |
| `router.ts` (`threads.send`) | Dedupe por `clientNonce` era check-then-act: um retry na janela duplicava a mensagem do usuário e estourava 500 na unique. | `claimUserRun()` reserva task+run na mesma transação com o nonce; P2002 devolve o run existente sem gravar nada. |
| `packages/memory` (`commit`) | Read-modify-write da `revision` sem transação: edição concorrente violava a unique **depois** de sobrescrever o conteúdo. | Compare-and-set com retentativas. Bug extra: a busca usava `userId`, que não faz parte da unique — outro membro do workspace tomava 500. |
| `packages/core/plans.ts`, `billing.ts` | Stripe `incomplete` virava `past_due` e o checkout recusava enquanto houvesse `stripeSubscriptionId`: um checkout preso em 3DS trancava o workspace por ~23 h. `periodStart` transbordava nos dias 29–31. | `incomplete` é status próprio e não bloqueia; novo checkout permitido; `Date.UTC` com clamp de dia. |
| `packages/auth` | Criação de org/member não era atômica: falha no meio deixava usuário sem workspace. | `provisionUserWorkspace()` transacional e idempotente. |
| `packages/core/approvals.ts` | `^mcp__[^_]+__` não removia o prefixo quando o servidor MCP tinha `_` no nome. | `^mcp__.+?__`, num helper único. |
| `packages/core/secrets-guard.ts` | Sem `SANDBOX_SUPERVISOR_TOKEN`, o token do supervisor **era o `BETTER_AUTH_SECRET`**: quem tivesse o segredo de sessão criava containers e executava comandos em qualquer workspace. | Em produção a credencial própria é obrigatória (o boot falha sem ela e recusa placeholder de dev ou o próprio segredo de auth). Fora de produção o token é derivado por HMAC — o segredo de sessão nunca chega ao supervisor. |

### Supervisor de sandbox (`infra/sandboxes/supervisor`)

| O que acontecia | Como ficou |
| --- | --- |
| O `env` do request era concatenado **depois** do `DISPLAY` da sessão: um bot mandava `env:{DISPLAY:":2"}` e operava a tela de outro bot do mesmo workspace. | O `DISPLAY` da sessão é autoritativo; nomes de variável validados e quantidade limitada; `argv` recusa NUL. |
| Após restart do supervisor os mapas em memória zeravam e o próximo bot recebia o display 1, derrubando o Xvfb de quem estava trabalhando. | Sonda o container e semeia os displays vivos antes de alocar. |
| A sonda de "há sessão rodando?" tinha `.catch(() => "")`: falha virava "ninguém trabalhando" e o container **do workspace inteiro** era removido. | Falha da sonda é lida como ocupado (fail-safe). |
| Comparação de token vazava o tamanho, `bearer` minúsculo falhava e token vazio passava. | Comparação por digest, esquema case-insensitive, token vazio recusado. |
| Todo erro virava 500 com a mensagem do Docker (caminhos do host, socket); no `/exec` virava `200 {code:1}`, escondendo até falha de autorização. | Mensagens estáveis por status (400/403/404/409) e o resto vira "computer request failed", com o detalhe só no log. |
| Falha transitória ao preparar a imagem ficava em cache para sempre. | A rejeição é esquecida. |
| `/exec` respondia sempre `stderr: ""` (frames do Docker concatenados). No provider **padrão**, um comando que falhava escrevendo só em stderr chegava ao agente como nenhuma saída — enquanto e2b e box entregavam stderr. | Demultiplexação por tipo de quadro, com orçamento único, quadros partidos entre chunks e UTF-8 preservado. |

### Clientes (`apps/web`, `apps/mobile`, `packages/ui-web`)

| O que acontecia | Como ficou |
| --- | --- |
| Cada `refreshThread` com o painel aberto pedia um `screenUrl` novo (TTL 60 s); a string mudava e o iframe do noVNC reconectava no meio da sessão. O mobile era pior: remontava a WebView a cada 2 s. | Política própria (`screen-url.ts`): a URL fica estável enquanto o iframe está montado e só troca quando aponta para outra tela. |
| O `embed.html` fazia `new RFB(...)` uma vez, sem handler de desconexão: um blip de rede congelava a tela do bot até o usuário fechar e reabrir o painel — e a capability já expirada impedia reconectar. | Retry local curto enquanto a capability vale; esgotada, avisa o app, que minta uma URL nova e remonta com backoff (4 tentativas) e depois mostra um estado claro de "caiu e não voltou". Vale para web e mobile. |
| Cada avatar montava 1–2 loops de `requestAnimationFrame` e um `pointermove` sem throttle. | Um rAF, um listener de ponteiro e um IntersectionObserver compartilhados; animação pausa fora da viewport. |
| `messageVersions` era O(n) duas vezes por mensagem por render (O(n²) durante streaming). | `versionsByParent` memoizado. |
| Num 401 o token era limpo mas o feed continuava reconectando com backoff, mostrando "Sessão expirada". | Primeiro 401 para o feed e leva ao login. |
| Lista de mensagens em `ScrollView`. | `FlatList` virtualizada, com as linhas calculadas por uma função pura. |
| ~7,4 MB de PNGs não referenciados. | Removidos após conferência. |

### Desktop, landing, lista de espera e operação

| O que acontecia | Como ficou |
| --- | --- |
| `second-instance` fazia só `win.show()`: janela minimizada não voltava. | `restore()` → `show()` → `focus()`. |
| `quibt://thread/thr_123` perdia o caminho e abria só `/thread`. | Host + path (e `#hash`) preservados, com segmentos `..` filtrados. |
| Uma falha de carregamento antiga substituía pela página offline a navegação nova em voo. | A página offline só entra quando a URL que falhou ainda é a pedida. |
| `pool.on("error")` ausente: um cliente ocioso derrubado pelo Postgres virava exceção não capturada e **matava a API** de waitlist. | Listener no pool; shutdown drena servidor e pool com prazo; boot com retry. |
| Falha na limpeza de retenção derrubava o cadastro do usuário e se repetia em toda requisição. | Agendador isolado com backoff. |
| `restore.sh` era destrutivo sem confirmação e rodava `psql` **sem `ON_ERROR_STOP`**: um dump quebrado "restaurava com sucesso" pela metade. | Exige confirmação explícita e usa `ON_ERROR_STOP=1 --single-transaction`; dump ausente aborta antes de tocar no banco. |
| `backup.sh` escondia falha do `tar` criando um arquivo vazio "com sucesso" e deixava dump parcial com cara de backup. | Escreve `.partial`, valida e só então renomeia. |
| Nenhum serviço do compose tinha `restart:` e o worker corria com as migrações. | `restart: unless-stopped`, healthcheck no api e `depends_on: service_healthy` no worker e no web. |
| `astro.config.mjs` declarava origem diferente da usada nos canonical/OG; não havia `robots.txt` nem `sitemap.xml`; `/pricing` servia português com `<html lang="en">`. | Origem alinhada, sitemap com hreflang gerado a partir das rotas, `/pricing` em pt-BR e fora do índice. |

## Rodada de release (mesma data)

Correções extras antes de liberar o open source + Cloud:

- `createGroupWakes` ficou idempotente (nonce dentro da transação + P2002); retry não reenfileira runs.
- `IsolationError` vira 404/409/400 em vez de 500.
- Retry de `threads.send` devolve o `seq` real; `computer.boot` usa `deps.dataDir`.
- Sign-up falha fechado (503) se a leitura de `deployment_settings` quebrar.
- Rotina órfã (bot/thread sumiu) se aposenta em vez de ficar agendada para sempre.
- `failRun` limpa o lease; deny de aprovação marca o effect como failed; `spawn_bot`/`delete_bot` não completam o effect duas vezes.
- `bots.get` não lista o workspace inteiro; rate-limit no teto evicta o mais antigo.
- UI: BurstSummary, chrome e placeholder da tela em português; stop no grupo; trackpad com saída; controles mortos removidos.
- `Shell.tsx` perdeu ~200 linhas (evento, form, screen helpers extraídos).
